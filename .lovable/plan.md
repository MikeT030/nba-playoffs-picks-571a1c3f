
# Share Wade's recaps across users (admin-only writes)

Today recaps live in `localStorage`, which is per-browser and per-origin — that's why production looks empty. Goal: recaps generated by an admin show up for every visitor on every device, while keeping the current UX snappy and degrading gracefully if the backend hiccups.

The constraint that **only admins ever generate recaps** removes most of the risk surface (no spam, no profanity moderation, no race conditions between users, no anonymous abuse). That lets us pick the simplest possible shape.

## What changes

Three layers:

1. **New table `demo_game_recaps`** — one row per (series, game), holds the latest summary plus who wrote it and when.
2. **`src/lib/demoRecapStore.ts`** — becomes a thin cache in front of the table. Reads return the local value synchronously (no UI lag), then revalidate from the table in the background. Writes go to the table first, then mirror to localStorage.
3. **`src/components/DeadpoolRecapDrawer.tsx`** — on successful generate, upsert to the table. Show a small "Saved · visible to everyone" hint after a successful write, or "Saved locally only" if the write failed.

No changes to the edge function. No changes to `MatchDetailDialog` / `DemoMatchDetailDialog` consumers — they keep calling `useDemoRecap(key)` and just start receiving shared data.

## Risk management with the admin-only constraint

| Risk | Without admin constraint | With admin-only writes |
|---|---|---|
| Spam / abuse on public table | Real | Eliminated — RLS blocks non-admins |
| Off-brand / profane content shown to all visitors | Real, needs moderation | Admin owns it; same trust level as today's manual content |
| Race conditions / last-write-wins clobbering | Real (two users hit Generate) | Eliminated — only one admin writing at a time in practice |
| Recap visible to logged-out visitors | Intentional, but raises content-quality bar | Fine — same content the admin already curates |
| Cloud outage breaks reads | Drawer goes blank | localStorage cache keeps last-known recap visible |
| Cloud outage breaks writes | Recap lost | Falls back to localStorage; admin sees "saved locally" toast and can retry |
| Read latency on every dialog open | Noticeable | Hidden behind synchronous local cache; network fetch is background revalidation |
| Stale recap after score correction | Real | Admin clicks Regenerate; same as today |
| Type regen of `supabase/integrations/types.ts` | Auto | Auto, no action |
| Existing local recaps "disappear" on production | Real | Admin regenerates the handful of games that matter — acceptable, no auto-migration |

Net: with admin-only writes, the only meaningful residual risks are **(a)** background fetch latency (mitigated by sync cache) and **(b)** Cloud outage during a write (mitigated by local fallback + toast). Both are graceful, neither breaks the app.

## Database

Single migration:

```sql
create table public.demo_game_recaps (
  series_id text not null,
  game_number integer not null,
  source text not null default 'demo',          -- 'demo' | 'real' (future-proofing)
  summary text not null check (char_length(summary) <= 600),
  created_by uuid references auth.users(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (series_id, game_number, source)
);

alter table public.demo_game_recaps enable row level security;

-- Public read: anyone (incl. logged-out) can see recaps.
create policy "Recaps are viewable by everyone"
  on public.demo_game_recaps for select using (true);

-- Admin-only writes via existing has_role() function.
create policy "Admins can insert recaps"
  on public.demo_game_recaps for insert to authenticated
  with check (has_role(auth.uid(), 'admin'));

create policy "Admins can update recaps"
  on public.demo_game_recaps for update to authenticated
  using (has_role(auth.uid(), 'admin'))
  with check (has_role(auth.uid(), 'admin'));

create policy "Admins can delete recaps"
  on public.demo_game_recaps for delete to authenticated
  using (has_role(auth.uid(), 'admin'));

create trigger update_demo_game_recaps_updated_at
  before update on public.demo_game_recaps
  for each row execute function public.update_updated_at_column();
```

The `check (char_length(summary) <= 600)` defends against a malicious admin client; the edge function still caps at 400.

## Code changes

### `src/lib/demoRecapStore.ts`

- Keep the in-memory `Map` + `localStorage` exactly as today (sync read path stays fast).
- Add `hydrateRecapFromServer(key, seriesId, gameNumber, source)` that does a single Supabase `select` and updates the store + localStorage if the server has a value (or a newer one based on `updated_at`).
- Add `saveDemoRecapRemote(key, payload)` that does a Supabase `upsert` then mirrors to local. Returns `{ ok: boolean, error? }` so the drawer can toast on failure.
- `useDemoRecap(key, opts?)` gains an optional `{ seriesId, gameNumber, source }` so it can trigger the background hydration once on mount. Existing call sites keep working without changes; we add the opts where we have the info handy.

### `src/components/DeadpoolRecapDrawer.tsx`

- After `setDemoRecap(...)` on a successful generation, call `saveDemoRecapRemote(...)`.
- Show inline status under the Save button: "Saved · visible to everyone" (success) / "Saved locally — couldn't reach backend" (failure, with Retry).
- Gate the Generate button on `useIsAdmin()` so non-admins never see a write path. Display a read-only message ("Only admins can generate recaps") if a non-admin somehow opens it.

### Consumers (`MatchDetailDialog`, `DemoMatchDetailDialog`)

- Pass `{ seriesId, gameNumber, source }` into `useDemoRecap` so they trigger the background fetch on mount. No other UI change.

## Rollout

1. Run the migration.
2. Ship the code change.
3. Admin opens production and clicks Generate on the games that matter — those become the seed content. Old localStorage-only recaps stay visible to the original generator until they're overwritten or cleared (acceptable).

No data migration script — the existing local recaps were per-browser anyway, and the admin will want to regenerate with current data.

## Out of scope

- Realtime subscription (push updates to open dialogs). Not needed — visitors get the recap on next dialog open.
- Recap history / versions / pinning. One row per game is enough.
- Per-user "draft" recaps. Admin writes directly to production.
- Migrating existing localStorage entries up to the table.

## Verification

1. Migration runs cleanly; types regenerate.
2. As admin in preview: open a game, click Generate, see "Saved · visible to everyone".
3. In an incognito window (logged out) on the production URL: open the same game → recap appears.
4. As a non-admin authenticated user: Generate button is hidden / disabled; recap still visible.
5. Block the Supabase domain in devtools, then Generate → toast says "Saved locally", drawer still shows the text, no crash.
6. Block Supabase, reload a dialog that previously showed a server-side recap → cached local copy still shows.
7. Existing tests pass.
